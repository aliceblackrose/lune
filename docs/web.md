# Web development with Lune

Lune's web-development support is intentionally small and development-oriented. It keeps networking out of the core VM while making it practical to build and iterate on HTTP applications with the language as it exists today.

The repository provides:

- `lib/web.lune` — HTML escaping, URL percent encoding/decoding, query parsing, response helpers, a small route dispatcher, and request decoding.
- `tools/lune_web.py` — a dependency-free development HTTP server built on Python's standard library.
- `examples/web/app.lune` — a minimal HTML/JSON application.

The server starts one Lune process per request. This gives a simple reload-on-request development loop without adding socket, concurrency, or async primitives to Lune 0.1. It is not intended as a production HTTP server.

## Run the example

Build Lune, then start the development server from the repository root:

```sh
make
python3 tools/lune_web.py examples/web/app.lune --lune bootstrap/build/lune
```

Open `http://127.0.0.1:8080/` or request the JSON endpoint:

```sh
curl 'http://127.0.0.1:8080/api/hello?name=Alice%20Blackrose'
curl -X POST -H 'content-type: text/plain' --data 'hello' \
  http://127.0.0.1:8080/api/echo
```

The server defaults to `127.0.0.1:8080`. `--host`, `--port`, `--timeout`, and `--max-body` control the bind address, per-request application timeout, and maximum request-body size. `LUNE=/path/to/lune` can be used instead of `--lune`.

## Application contract

For each HTTP request, the development server invokes:

```text
lune app.lune REQUEST_JSON
```

`web.request()` reads and parses that argument. The request map contains:

```lune
{
    method: "GET",
    target: "/search?q=lune",
    path: "/search",
    query: "q=lune",
    query_params: {q: "lune"},
    headers: {"accept": "*/*"},
    body: "",
    remote_addr: "127.0.0.1",
}
```

Header names supplied by the development server are lowercase. Query parameters use form-style decoding: `+` becomes a space and valid `%HH` sequences are decoded. Duplicate query keys currently use the final value.

An application prints exactly one JSON response object to stdout:

```lune
{
    status: 200,
    headers: {"content-type": "text/plain; charset=utf-8"},
    body: "hello\n",
}
```

Use `eprint(...)` for application logging. Extra stdout output makes the response invalid by design, which keeps the bridge deterministic and easy to debug.

## Web helper module

Import the module with a path relative to the application:

```lune
web := import("../../lib/web")
```

The module exports:

- `escape_html(value)` — escapes `&`, `<`, `>`, double quotes, and single quotes.
- `percent_encode(text)` — UTF-8 byte-oriented URL percent encoding using the RFC 3986 unreserved set.
- `percent_decode(text)` — decodes `%HH` sequences and converts `+` to a space.
- `parse_query(query)` — parses an `a=1&b=2` query string into a map.
- `response(status, headers, body)` — constructs a response map.
- `text(body)`, `html(body)`, `json(value)` — `200` response shortcuts.
- `redirect(location)` — a `302` response.
- `not_found()` — a plain-text `404` response.
- `html_document(title, body)` — creates a minimal HTML document and escapes the title.
- `dispatch(routes, request)` — invokes a route handler.
- `request()` — decodes the development-server request argument and adds `query_params`.

Routes are map keys of the form `"METHOD /path"`. A path-only key is a fallback for all methods at that path, and `"*"` is the final fallback:

```lune
web := import("../../lib/web")
request := web.request()

routes := {
    "GET /": fn(req) => web.html("<h1>Hello</h1>"),
    "GET /api": fn(req) => web.json({ok: true}),
    "*": fn(req) => web.not_found(),
}

print(json_stringify(web.dispatch(routes, request)))
```

## Development-server limits

This bridge deliberately optimizes for a simple development loop rather than throughput:

- one fresh Lune process is started for every request;
- request bodies must be valid UTF-8 and are capped at 1 MiB by default;
- request bodies using chunked transfer encoding are not supported;
- response bodies are UTF-8 strings;
- `Content-Length` is generated by the adapter and cannot be overridden by the app;
- application response headers containing CR or LF are rejected;
- there is no TLS termination, WebSocket support, streaming, or persistent in-process application state.

These constraints give Lune enough web functionality for local application development, JSON APIs, forms, server-rendered HTML, and prototyping without prematurely committing the VM to a networking/concurrency model. A future native HTTP/socket layer can preserve the same request/response shape if real programs justify it.
